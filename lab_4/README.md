# Warehouse Management System (WMS) API

Добро пожаловать в репозиторий сервиса складского учёта. 

Проект реализует эволюцию архитектуры: от простого кеш-сервиса до распределенной системы с обеспечением строгой и итоговой согласованности.

## Версионирование API

### `v1` — Legacy / Fast Reservation
Простая и быстрая система резервирования товаров.
* **Стек:** Redis (основное хранилище резервов) + MongoDB (каталог).
* **Особенности:** Использует TTL для автоочистки корзин. Идеально подходит для высоконагруженных распродаж, где важна скорость, а строгая транзакционность вторична.
* **Эндпоинты:** `/api/v1/...`

### `v2` — Distributed Inventory & Accounting (Текущий фокус)
Полноценная система складского учёта.
* **Стек:** PostgreSQL (остатки/транзакции) + MongoDB (события) + Redis (быстрые блокировки).
* **Особенности:** Поддержка CQRS, Event Sourcing и распределенных транзакций (Saga).
* **Эндпоинты:** `/api/v2/...`

---

## Архитектура v2 (Polyglot Persistence)

Каждая база данных используется для решения своей специфической задачи:

1. **PostgreSQL (Source of Truth для состояния):**
   * Хранит каталог товаров, справочник складов и **текущие фактические остатки**.
   * Обеспечивает ACID-транзакции при списании и приёмке товара.
2. **MongoDB (Event Store / Журнал):**
   * Хранит события движения товаров (Event Sourcing).
   * Используется для CQRS-отчетности (аналитика, история движений, аудит).
3. **Redis (Оперативный слой):**
   * Хранит временные резервы (корзины) с TTL.
   * Служит механизмом быстрой блокировки (distributed lock) для предотвращения оверселлинга (overselling) в моменте.

## Ключевые паттерны (v2)

### 1. CQRS (Command Query Responsibility Segregation)
* **Write Model (Команды):** Запись новых остатков или резервирование идет через PostgreSQL и Redis. Это гарантирует, что мы не продадим больше, чем есть.
* **Read Model (Запросы/Отчеты):** Сложные отчеты (например, "история всех движений товара Х за год") формируются путем чтения событий из MongoDB, чтобы не нагружать транзакционную PostgreSQL.

### 2. Event Sourcing
Мы не просто обновляем цифру остатка (`stock = stock - 1`). Каждое изменение фиксируется как неизменяемое событие (`StockDecreased`, `StockReceived`, `ReservationCancelled`) в MongoDB. Текущий остаток в PostgreSQL — это лишь "снимок" (projection) суммы всех событий.

### 3. Distributed Transactions (Saga Pattern)
Поскольку у нас нет единой распределенной транзакции на 3 разные БД, мы используем паттерн **Saga (Оркестрация)** с компенсирующими действиями для сценария подтверждения покупки.

#### Flow Саги при подтверждении заказа (`ConfirmOrder`):
1. **Шаг 1 (Postgres):** Уменьшаем фактический остаток на складе.
   * *Успех:* Идем дальше.
   * *Ошибка (нет товара):* Отбой, возвращаем ошибку пользователю.
2. **Шаг 2 (MongoDB):** Сохраняем событие `OrderConfirmed` / `StockDecreased`.
   * *Успех:* Идем дальше.
   * *Ошибка (MongoDB упала):* **Компенсация:** Возвращаем товар в Postgres (`stock = stock + 1`). Отбой.
3. **Шаг 3 (Redis):** Удаляем резерв из корзины пользователя.
   * *Успех:* Сага завершена.
   * *Ошибка (Redis упал):* Так как фактический остаток в Postgres уже корректен, а событие в Mongo записано, мы логируем ошибку и ставим задачу в фоновый воркер на принудительную очистку ключа в Redis.

## Вывод по надёжности схемы (Reliability Analysis)

При проектировании v2 были учтены следующие риски и способы их митигации:

1. **Рассинхронизация данных (Eventual Consistency):**
   * *Риск:* Событие в MongoDB может быть записано с задержкой относительно обновления в PostgreSQL.
   * *Решение:* Бизнес-процессы (покупка) опираются на PostgreSQL. Отчетность (CQRS) в MongoDB допускает задержку (итоговая согласованность). Для критичных отчетов внедрен механизм пересчета проекций.
2. **Отказ промежуточного узла (Saga Failures):**
   * *Риск:* Падение одной из БД в середине Саги.
   * *Решение:* Реализованы компенсирующие транзакции. Если шаг 2 упал, шаг 1 откатывается. Для шага 3 (Redis) используется идемпотентный фоновый клинер.
3. **Дублирование событий (Idempotency):**
   * *Риск:* При ретраях (retry) одно и то же событие может быть отправлено в MongoDB дважды.
   * *Решение:* Каждое событие имеет уникальный `event_id`. В MongoDB настроен `unique index` по этому полю. При дубле операция просто игнорируется.
4. **Проблема "Гонки" (Race Conditions):**
   * *Риск:* Два пользователя пытаются купить последний товар одновременно.
   * *Решение:* В PostgreSQL используются атомарные операции (`UPDATE ... WHERE stock >= qty`), а в Redis — атомарные Lua-скрипты или `HINCRBY` с проверкой лимитов.
5. **Уязвимость Redis (In-Memory):**
   * *Риск:* При перезагрузке Redis без персистентности все брони "сгорят".
   * *Решение:* Так как Redis в v2 используется лишь как быстрый lock/кэш, а "истиной" является PostgreSQL, потеря Redis приведет лишь к временному снятию броней, но не к оверселлингу или потере данных о продажах. Настроен Redis Sentinel и AOF для минимизации простоев.
